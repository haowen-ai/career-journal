# CAREER JOURNAL 2.0 设计：先问清楚，再帮你投

[English](2026-10-01-career-journal-2.0-design.en.md) | [简体中文](2026-10-01-career-journal-2.0-design.md)

**状态：** 设计稿，待确认
**日期：** 2026-10-01
**目标版本：** 2.0.0
**基于：** 1.1.0（测评与面试准备、测评链接、Claude Code 定时任务）

## 1. 一句话

1.x 只负责记录：投了什么、到了哪一步、哪天截止。2.0 在此基础上，从找岗位到填好申请表全程帮用户做，只把登录、验证码、同意、签名和最后的提交留给用户本人。因为每个人要找的岗位和要填的答案都不一样，2.0 第一次使用时先问清楚用户的情况，之后所有扫描和填表都只用这份资料。

## 2. 为什么要做

作者本人在 2026 年 9 月底用 Agent 投了约 80 份 Summer 2027 实习，流程已经跑通：

- 每天扫描新开的岗位，按方向、地点、学历和身份筛选，再按匹配度排队；
- Agent 每次拿 5 个岗位，在用户的 Chrome 里各开一个标签页填表，停在提交前；
- 用户登录、输验证码、勾同意框、签名、点提交；
- Agent 查确认邮件，把状态改成已投递；收到测评邀请时记下截止时间和链接。

但这套东西只存在于作者的本机：填表规则、答案表、各招聘网站的填法经验、扫描脚本都写死了作者本人的信息。别人 clone 项目后用不了。2.0 要把它做成通用功能。

## 3. 目标与非目标

### 3.1 目标

1. **初次问答**：clone 后由 Agent 分几轮问清用户的求职目标、材料和常见表单答案，存在用户本机。
2. **每日扫描**：按用户自己的条件找新岗位，核实官网，排好队放进看板。
3. **分批填表**：Agent 在用户浏览器里按答案表填申请，停在提交前。
4. **投后核对**：用确认邮件核对是否真的投出；测评和面试邀请自动进入“测评与面试准备”。
5. **边投边问**：遇到答案表没有的新题才问用户，答案存下来下次直接用。
6. **老用户无缝升级**：1.x 已有的记录和资料自动带入，只补问缺的。

### 3.2 非目标（与 1.x 一致，不放宽）

- **不替用户点最终提交**。任何写着 Submit / 提交 的按钮都由用户点。
- **不替用户登录、注册账号、输入密码或验证码**，不绕过 CAPTCHA。
- **不替用户勾同意、声明、仲裁条款，不代签电子签名**。
- **不替用户写作文**（why us、cover letter 等）。只能整理用户自己说的话。
- **不做测评、不参加面试**。
- 不把用户个人资料写进仓库、日志或发给第三方。

## 4. 参与者

| 角色 | 负责什么 |
|---|---|
| 用户 | 回答初次问答；登录、验证码、同意、签名、提交；回答遇到的新题 |
| Agent（Codex / Claude Code 等） | 问答、扫描、排队、派填表任务、查邮件、更新记录 |
| 填表子 Agent | 每个只负责一个岗位，在自己的浏览器标签页里填表 |
| 浏览器能力 | Claude in Chrome、Codex 浏览器等，宿主有什么用什么 |
| Jev（可选） | 判断匹配度、二选一、拿不准的题；没有 Jev 时由当前 Agent 判断 |
| CAREER JOURNAL 核心 | 保存资料、岗位队列、申请记录、测评任务；看板展示 |

## 5. 总体流程

```
初次问答 ──> 个人资料（本机）
                 │
每天定时扫描 ──> 按资料筛选、核实官网、打匹配度 ──> 看板「准备中」队列
                 │
用户说「开始投」 ──> 每批 N 个（默认 5） ──> 子 Agent 各开标签页填表
                 │                              │
                 │               需要用户时：标签标题改成 🔑待登录 / ❓待回答 / 👆待点击
                 │                              │
                 │               填完：标签标题改成 ✅待提交，停在提交前
                 │
用户登录、验证码、同意、签名、提交
                 │
查确认邮件 ──> 状态改为已投递；测评邀请 ──> 「测评与面试准备」（截止时间 + 链接）
```

## 6. 初次问答

在现有 onboarding（邮箱、定时任务、doctor）通过之后进行。每轮最多 4 个问题，用选项加“其他”的形式问，每题都能跳过，跳过的题在第一次用到时再问。能从简历读出来的先读，只让用户确认。

### 第 1 轮：找什么（决定扫哪些岗位）

| 问题 | 用途 | 例子 |
|---|---|---|
| 实习还是全职，哪一季 | 只扫这一季 | Summer 2027 实习 |
| 方向，分主次 | 筛选和匹配度 | 主：AI / ML / 数据；次：量化 |
| 地点，按先后排；是否接受远程 | 筛选和选办公室 | 纽约 > 西雅图 > 湾区 > 美国远程 |
| 学历、专业、毕业时间 | 筛掉只招本科、只招博士、毕业时间不符的岗位 | 硕士，2027 年 12 月毕业 |
| 工作身份 | 筛掉要求公民身份或安全许可的岗位；回答担保题 | 绿卡，不需要担保 |
| 一定不要的 | 筛选 | 明确不给转正的岗位 |

### 第 2 轮：材料

- 简历文件。默认所有岗位用同一份；用户想按岗位换版本时，走现有的 `careerops-materials` Skill。
- 成绩单（可选）。**只在网站把成绩单设为必填时才上传**，不放进“其他附件”。
- LinkedIn、GitHub、个人网站。
- 从简历读出学历和每段工作经历（公司、职位、地点、起止年月、每条 bullet），让用户逐段确认。填表时工作描述按“每条一行，行首加 •”写入。

### 第 3 轮：常见表单题

先问最常见的一组，生成用户自己的答案表：

- 姓名、偏好名、邮箱、电话、地址
- 自愿披露：性别、族裔、退伍军人、残障。每一项都可以选“不愿透露”
- 语言和水平
- 到岗时间、能否全职、通知期
- 期望薪资的写法（例如“与岗位公布的范围一致”，不写具体数字）
- 是否第一代大学生、是否有亲属在政府或该公司工作、是否签过竞业或保密协议
- 证书、获奖

### 第 4 轮：规矩和节奏

- 一批投几个（默认 5）
- 每天几点扫描、怎么通知（默认桌面通知）
- 第 3.2 节的硬规矩会展示给用户看，不能关闭

### 边投边问

填表时遇到答案表里没有的必填题，子 Agent 停下，标签标题改成“❓待回答”，主 Agent 把原题和选项转给用户。用户回答后写回答案表，注明日期和“用户确认”，以后同类题直接用。

## 7. 个人资料放在哪

- 全部放在用户的数据目录（例如 `~/job-search/.career-journal/profile/`），**不进 Git 仓库**：
  - `profile.json`：第 1、2、4 轮的结构化答案（方向、地点、学历、身份、批次大小等）
  - `answers.md`：第 3 轮和边投边问攒下的表单答案，中英文都可以
  - 简历、成绩单只记文件路径，不复制
- 仓库里只放空白模板 `config/profile.template.json` 和 `config/answers.template.md`，以及问题清单。
- 发布检查新增一项：仓库里不得出现任何真实的姓名、邮箱、电话或地址。

## 8. 每日扫描

- **来源**（都只读）：
  - 默认：用户列出的公司在官方招聘系统上的公开岗位接口（Greenhouse、Lever、Ashby）
  - CareerOps 的公司门户扫描（可选依赖，MIT 许可证，沿用现有署名）
  - SimplifyJobs 公开列表：它没有开源许可证，所以**只作为用户自己选择开启的来源**，在用户电脑上扫描时实时读取；项目里不打包、不缓存、不转发它的数据
- **筛选**：全部来自 `profile.json`，不写死任何人的条件。
- **去重**：同一岗位编号、同一链接、或公司加岗位名高度相似的，视为同一个岗位，不重复投。
- **核实**：对新进队列的岗位读官网原文，检查学历要求、毕业时间、身份要求、是否明确不给转正、是否已关闭、截止日期、有没有必答作文。不符合的标记为“不投”并写明原因。
- **公司规则**：例如“每人只能投一个岗位”，由 Jev 或 Agent 选最对口的一个，其余标记“不投”并写原因。
- **结果**：进入看板“准备中”，发一条桌面通知，写一份当天的中英文小结。

## 9. 分批填表

- 新增 `career-journal-apply` Skill（中英文各一份），内容来自这次实践：
  - 每个子 Agent 只填一个岗位、只用自己新开的标签页，不碰别人的标签页；
  - 先查是否已投过；不招用户学历、地点不符的不投；
  - 按答案表填；简历固定用用户指定的那份；
  - 标签标题约定：🔑待登录、🤖待验证、❓待回答、👆待点击、✅待提交；
  - 各招聘系统的填法要点：Workday、Oracle、iCIMS、Greenhouse、Ashby、Lever、Yello、SuccessFactors（例如 Workday 下拉框怎么选、iCIMS 的表单在 iframe 里、Greenhouse 要先显示页面才加载）；
  - 第 3.2 节的硬规矩。
- 主 Agent 收到每个子 Agent 的报告后，用一句话告诉用户哪个标签页要做什么。
- 浏览器断开或标签页被关时，已经保存的步骤从网站草稿继续，没保存的从头重填。

## 10. 投后核对

- 用户提交后，Agent 查确认邮件或网站的“已收到”页面，有证据才把状态改为已投递，并记一条事件说明证据。
- 收到测评或面试邀请：用 `task add` 记录，带截止时间（含时区，写明怎么推算）和邀请链接。
- 扫描产生的重复记录标记为“重复”，指向保留的那一条。

## 11. 数据和命令改动（初步）

- 新命令：`career-journal profile show|set|interview`、`career-journal scan run`、`career-journal queue list`。
- `applications` 增加来源编号、匹配度、核实结果等字段（数据库结构版本 5）；队列就是状态为“准备中”的申请，不另建表。
- 看板“准备中”显示匹配度、截止时间和“不投”原因。
- 具体字段在实现计划里定。

## 12. 从 1.x 升级

- 已有的申请、事件、测评任务原样保留。
- 第一次运行 2.0 时，如果没有 `profile.json`，Agent 先从已有记录、简历和配置里推断能推断的内容，只问缺的；推断出来的每一项都要用户确认。
- 数据库按现有规则升级：先 `migrate --dry-run`，再备份，再 `migrate --apply`。

## 13. 为什么是 2.0

初次使用流程（AGENTS.md 和 Skill 里的 onboarding 契约）多了必经的个人资料问答，项目的定位也从“记录”变成“记录加代填”，所以按语义化版本升主版本号。

## 14. 怎样算做完

1. 一个从没用过的人 clone 后，Agent 能问完四轮问题，生成他自己的 `profile.json` 和 `answers.md`，仓库里没有任何作者本人的信息。
2. 扫描只按这个人的条件出结果，每个“不投”都有原因。
3. 拿 5 个不同招聘系统的岗位试填，都能停在提交前；需要用户时标签标题正确。
4. 没有任何一次替用户点提交、输密码或验证码、勾同意或签名。
5. 提交后能用确认邮件把状态改成已投递；测评邀请带截止时间和链接出现在看板上。
6. 从 1.1.0 升级：已有数据完整，只补问缺的资料。
7. 发布前通过全部测试、发布检查、全新 clone 测试和从 1.1.0 升级测试。

## 15. 风险和待定

- **招聘网站的条款**：只做用户本人在自己浏览器里的代填，不批量、不绕过验证；仍由用户点提交。
- **浏览器能力不稳定**：扩展会掉线、标签组会被关，所以每一步都要能从网站草稿或从头恢复。
- **第三方数据的许可**：已核对，SimplifyJobs 列表没有开源许可证，按第 8 节只做用户自选、本机实时读取；CareerOps 是 MIT。两者都在 `THIRD_PARTY_NOTICES` 里写明。
- **Jev 可选**：没有 Jev 时匹配度和拿不准的判断由当前 Agent 做，并在记录里注明。
